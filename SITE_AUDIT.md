### 2. SEARCH IS BROKEN FOR 95%+ OF CONTENT (LIVE)

**What:** The pagefind search index on the live site was built on **2026-04-06 with only 39 pages**. The site now has 814+ live articles. Searching for any error code added after April 6 returns zero results.

**Evidence:**
- `dist/pagefind/pagefind-entry.json`: `{"page_count":39}` with `LastWriteTime: 4/6/2026 10:17:11 PM`
- Live site now has 814 blog post folders
- The search page at `/search/` loads and shows the UI, but 97%+ of articles are invisible to it

**Root cause:** The `build` script in `package.json` runs `pagefind --site dist` after each build AND then copies the index to `public/pagefind/`. When the site had only ~39 articles, this was last run successfully. The subsequent mass article additions (batches 1-18, 770 affiliate injections) were committed and deployed WITHOUT rebuilding the pagefind index. The old index was baked into deployments via the `public/pagefind/` copy.

**The full build command is:**
```
astro check && astro build && pagefind --site dist && xcopy /E /I /Y dist\pagefind public\pagefind
```
The pagefind rebuild is bundled into `pnpm run build`. Once the build is fixed (Issue #1), pagefind will automatically reindex all articles.

**Fix:** Fix issue #1 (run successful build). Pagefind runs automatically as part of `pnpm run build`.

## 🟠 HIGH PRIORITY

### 4. ROBOTS.TXT HIJACKED BY CLOUDFLARE

**What:** The live `https://errorcodefixes.com/robots.txt` returns a Cloudflare-generated "AI content signals" file instead of the standard robots.txt generated by `src/pages/robots.txt.ts`.

**Live robots.txt (wrong):**
```
# As a condition of accessing this website, you agree to abide by the following
# content signals:
# (a) If a content-signal = yes...
[Cloudflare legal boilerplate about AI indexing]
```

**Expected robots.txt (from robots.txt.ts):**
```
User-agent: *
Allow: /

Sitemap: https://errorcodefixes.com/sitemap-index.xml
```

**Impact:** Google and other crawlers aren't seeing the sitemap reference in robots.txt. This delays discovery of new articles. Also the current robots.txt is confusing and looks like a legal document.

**Root cause:** Cloudflare Pages may be generating this automatically when no `robots.txt` is found in the static output, OR it's overriding the Astro-generated one. The local `dist/` has no `robots.txt` file (it's generated by a dynamic route handler `.ts`).

**Fix — add a static `public/robots.txt`** that Cloudflare will use directly:
```
# public/robots.txt
User-agent: *
Allow: /

Sitemap: https://errorcodefixes.com/sitemap-index.xml
```
Then update `deploy.ps1` to copy it (the script already copies `_headers`, same pattern):
```powershell
Copy-Item "public/robots.txt" "dist/robots.txt" -Force
```
AND remove or rename `src/pages/robots.txt.ts` to avoid conflicts with the static file.

### 8. `astro check` MAY BE BLOCKING BUILDS

**What:** The build script is `astro check && astro build && pagefind...`. The `astro check` step runs TypeScript type checking. With 911 articles and a complex component tree, this can fail on minor type errors that don't affect actual output, blocking the entire build.

**Fix:** Consider splitting the build script to allow deploying even if type checking has warnings:
```json
"build": "astro build && pagefind --site dist && (xcopy /E /I /Y dist\\pagefind public\\pagefind)",
"typecheck": "astro check"
```
Run `pnpm typecheck` separately as a CI gate, not as part of the deployment path.
